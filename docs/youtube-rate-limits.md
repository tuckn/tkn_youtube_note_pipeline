# YouTube字幕取得制限の調査メモ

初回確認日: 2026-10-13。対象: tkn-youtube-note 0.3.8 / yt-dlp 2026.08.19 によるWeb経由の字幕取得。2026-10-17に0.3.10の字幕選択変更を追記しました。

## 0.3.10での字幕選択

メタデータの言語に非翻訳字幕があれば優先し、なければ `ja-orig` などの原語表示を持つ自動字幕を調べます。利用可能な非翻訳JSON3がある原語表示だけを採用し、その言語の非翻訳手動字幕、自動字幕の順で探します。原語表示が複数ある場合は取得情報の順を維持します。

見つからなければ、メタデータの言語（翻訳を含む）、設定した代替言語の順で探す従来の動作を維持します。原語表示のない別言語字幕を無条件に選ぶことはしません。保存済みのメタデータやRAWは書き換えません。

これにより、メタデータが `en-US` でも日本語原文の `ja-orig` が存在するケースでは、英語への自動翻訳より日本語原文を先に選びます。以下の2026-10-13の観測・未検証事項は当時の記録です。

2026-10-17の実通信検証では、この条件に該当する動画を0.3.10の通常の字幕選択・取得処理に通し、日本語原文571区間の取得と文字起こし検証に成功しました。ブラウザCookieの読取りや待機の追加は行わず、一時保存先だけを使用しました。この1件の成功は、あらゆる429の解消や取得上限を保証するものではありません。

## 結論と確度

Web字幕取得の許容本数・要求回数・制限解除時間を保証するYouTube公式の数値は、今回確認した公式資料では見つかりませんでした。429を「1日何本まで」「一定時間で必ず解除」と読み替えないでください。HTTP 429、YouTube Data APIのquota、yt-dlp利用時の制限・不具合は分けて扱います。

| 区分 | 確認できること | このCLIへの適用 |
| --- | --- | --- |
| HTTPの標準仕様 | 429は一定時間内の要求過多を表す。`Retry-After` に待機時間を示すことがあるが、付与は必須ではない。利用者の識別方法や回数の数え方は規定していない。 | 429だけでは閾値・対象・解除時刻を特定できない。[RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585#section-4) |
| YouTube公式のAPI仕様 | YouTube Data APIにはプロジェクト単位のquotaがある。 | 本CLIはそのAPIを使わず、yt-dlpでWeb情報と字幕を取得する。APIのquotaやリセット時刻を転用できない。[公式API概要](https://developers.google.com/youtube/v3/getting-started#quota) |
| yt-dlpプロジェクトの説明 | FAQは429を過剰利用によるIPアドレスのブロックとして説明している。 | 一般的な診断の手がかりであり、字幕の429すべての原因を確定するものではない。[FAQ](https://github.com/yt-dlp/yt-dlp/wiki/FAQ#http-error-429-too-many-requests-or-402-payment-required) |
| yt-dlp開発者の字幕固有の報告 | Issue #13831の2026-01-06付の説明は、自動翻訳字幕に対象を限定している。 | 通常の回数制限と区別する。元言語の自動字幕があれば、この種類の問題を避けられる可能性があるが、あらゆる429を防げる保証ではない。[Issue #13831](https://github.com/yt-dlp/yt-dlp/issues/13831) |

## ネット上の数値は、何に対する目安か

yt-dlp Wikiには、ゲスト約300動画/時（Webページ・player要求約1,000回/時）、アカウント利用時約2,000動画/時（同約4,000回/時）という概数と、ダウンロード間に約5〜10秒置く推奨があります。ただし、これは `This content isn't available, try again later` という動画要求エラーの説明です。YouTube公式の保証値でも、字幕の安全な取得上限でもありません。1動画の処理で複数のHTTP要求が発生するため、本数と要求回数も一致しません。[yt-dlp Extractors Wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#common-youtube-errors)

字幕については、同じIssueに「60秒の待機で自動翻訳字幕を取得できた」という2026-07-24の利用者報告と、「61秒待っても429になった」という報告の引用があります。環境・字幕・要求の条件が違うため、60秒を保証値として採用できません。[Issue #13831の利用者報告](https://github.com/yt-dlp/yt-dlp/issues/13831)

yt-dlp単体には `--sleep-requests`（情報抽出中の要求間）と `--sleep-subtitles`（字幕ダウンロード前）があります。動画ダウンロードの待機指定と字幕の待機指定は区別されています。動画間に要約処理を挟むことと、動画情報を取得してから字幕を要求する前に待つことも同じではありません。[yt-dlpのオプション定義](https://github.com/yt-dlp/yt-dlp#workarounds)

## このCLIでの実測と診断

2026-10-13の逐次処理で保存したmanifest・動画情報・実行レポート、および現在の字幕選択処理を確認しました。以下は一度の観測で、制限値の測定実験ではありません。

| 観測項目 | 結果 |
| --- | --- |
| 処理 | 動画本体を取得せず、1本ずつ字幕取得・文字起こし・要約を実行 |
| 成功と失敗 | 15本成功後、16本目の字幕要求で `HTTP Error 429: Too Many Requests` |
| 経過時間 | 初回取得開始から失敗した取得の開始まで約15分 |
| 取得開始間隔 | 約51〜74秒、平均約60秒。取得と要約の実行時間を含む |
| 成功した字幕 | 非翻訳の日本語自動字幕14本、自動翻訳扱いの日本語字幕1本 |
| 失敗時の状態 | 動画情報取得は成功。メタデータの `language` は `en-US`、選択された字幕は `en`。字幕URLに翻訳先を示す `tlang` があった |
| 別の字幕候補 | 同じ保存済み動画情報に、翻訳要求を伴わない日本語字幕候補も存在した |
| 復旧状況 | 429後に新たな取得は行っていない。制限解除時間・他の動画の取得可否・原語字幕での成功は未検証 |

### なぜ日本語動画で英語字幕が選ばれたのか

調査時の0.3.8の `select_caption()` は、動画情報の `language`（なければ `original_language`）を原語として扱い、その言語に一致する字幕を探していました。非翻訳優先は、その候補言語の中で行い、すべての字幕言語から元音声の言語を再判定する処理ではありませんでした。

そのため、今回の保存済み情報では `en-US` → `en` の自動翻訳字幕が選ばれました。`fallback_languages: [ja]` を指定しても、英語の候補が見つかった段階で選択が終わるため変わりません。ダウンロードが429になってから別言語を試す機能もありません。`--summary-profile default-ja` は要約言語の指定であり、取得字幕の言語は変更しません。

ネットワークを使わず、保存済み情報のコピー上で原語指定を日本語に変えた場合には非翻訳の日本語字幕が選ばれることを確認しました。これは選択処理の診断であり、取得成功の確認や保存済みRAWの変更ではありません。

**推測:** 今回の失敗は、自動翻訳字幕の制限・認証条件に関係している可能性があります。通常の回数制限、接続元やセッションによる判定、複数要因の組み合わせも排除できません。日本語への翻訳扱いの字幕は1本成功しているため、「翻訳字幕は必ず失敗する」とも言えません。したがって「15本が上限」「待つだけで直る」「IP全体がブロックされた」とは断定しません。

## 再開時の暫定運用案

以下は本プロジェクトでの運用上の提案です。YouTubeの公式仕様・実測済みの安全値・CLIに実装済みの自動制御ではありません。

1. 429を検出したら連続取得を止め、失敗段階と字幕言語を調べます。取得済みファイルを削除したり、`--force` / `--refresh` で制限を解除しようとしないでください。
2. 自動翻訳が選ばれている場合は、元言語の字幕候補とメタデータの言語を確認します。今回のように両者が食い違う場合、待機時間だけでなく字幕選択の見直しが必要です。
3. 一般的な回数超過が疑われる場合、取得できた応答に `Retry-After` があれば従います。本CLIはこのヘッダーを専用項目として保存・処理しておらず、今回のログからは有無も値も確認できません。指示が分からなければ、まず30〜60分休止して1本だけ試し、なお失敗する場合は数時間〜翌日に延ばす、という保守的な運用を提案します。待機だけでの回復は保証しません。
4. 復旧後は並列取得を避け、5〜10本程度の小さな単位で状況を確認する案が考えられます。この本数も上限や安全値ではありません。今回のように約1分間隔でも失敗し得るため、単に待機秒数を固定して解決済みとしないでください。
5. 取得済みの字幕は再利用します。成功したmanifestがあれば `build-source`、文字起こしがあれば `build-summary` から再開できます。`ingest` の再実行はYouTubeへの取得要求を伴います。

現在のCLIには、取得間隔の設定、429後の待機・自動再開、字幕言語の直接指定、ブラウザCookieやPO Tokenを渡すための専用オプションはありません。yt-dlp単体のオプションを、そのまま `tkn-youtube-note` の引数や設定に追加することはできません。原語字幕の判定は0.3.10で改善しました。今後の改善候補は、字幕取得前の待機、診断情報の充実です。

## 調査の限界

YouTube側の内部判定・閾値・接続元の評価は確認できていません。今回の調査では字幕取得の再試行、ブラウザCookieの読取り、アカウント認証、接続元変更は行っていません。Web上の資料は更新され得るため、再調査時は確認日と実際のyt-dlpバージョンを記録してください。ローカルのフルパス、署名付き字幕URL、Cookieなどは公開用の診断報告に含めないでください。
